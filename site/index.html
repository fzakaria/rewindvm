Deterministic Linux VMs

Scrub any run back to the step that broke it.

Rewind VM runs a Nix build, a test suite or any Linux command inside a deterministic KVM virtual machine. The same inputs produce the same run, instruction for instruction, every time. When it fails, drag the timeline back to where it went wrong, look around, and fork from there.

How it works

Nothing is recorded while the workload runs. A run is a function of its inputs, so any step of it can be computed again.

  1. Pack the inputs

    The inputs, a Nix closure or any root filesystem, become a read-only erofs image mapped straight into guest memory. A small Linux kernel boots and runs your command.

  2. Run deterministically

    One vCPU. The guest kernel carries a small Rewind hypervisor platform: virtual time moves only when the guest yields, interrupts are injected only at those points, and the timestamp counter and hardware RNG are hidden. Each guest-triggered exit is one step.

  3. Keep keyframes

    Snapshots use KVM dirty-page logging and go into a content-addressed page store (BLAKE3, zstd). A page that is identical across keyframes, runs and forks is stored once.

  4. Seek

    To reach a step, Rewind restores the nearest keyframe and runs forward to the exact step. Same inputs, same steps, same machine state.

In the desktop app

Scrub the timeline

Drag through the run and see the log up to that step, the processes alive at that step, the files written so far and the event at the step.

Jump to the divergence

Put a passing run next to a failing one and land on the first step where they differ.

Jump to the failure

The crash, the non-zero exit or the failed test, one click from anywhere.

Attach gdb at any step

Break into a process as it was at step 11,204 or step 3. Attaching does not change the run, so a race that hides from a debugger stays put.

Open a shell at a step

Look at the filesystem, the environment and the half-written output files exactly as they were.

Fork with a new seed

Branch from any step with a different seed and the threads interleave differently. Explore what else could have happened, Antithesis-style.

Fork with a changed file

Patch a source file or a config at a step and run on from there, without redoing everything before it.

Share a failure as a file

Export a failing run as a small file, attach it to an issue, and anyone with Rewind lands on the same step.

Bring a command, or bring a derivation

Any Linux workload

A root filesystem and a command

$ rewind run --image rootfs/ -- make check

The root filesystem can be a directory or an OCI or Docker image. Whatever runs in it runs deterministically.

flaky tests
Run a test under many seeds until it fails. That failing run can now be reached again, every time.
CI failures
CI keeps the failing run as a file. Open it on your laptop and scrub back from the red line instead of reading a log that ends at the crash.
heisenbugs
Races that vanish under a debugger stay put here. The run is fixed before gdb attaches.
exploration
Fork a passing run at a step with new seeds to try other thread interleavings from that point on.

For Nix users

Nix builds are already almost a closed world

$ rewind nix ./#mylib
$ rewind check ./#mylib

Pinned inputs, no network, fixed paths. Point Rewind at a flake attribute or a .drv and most of the work of making the run deterministic is already done.

.drv
The derivation hash is the unit of reproduction.
the machine
The guest kernel and the VMM are derivations too, so the whole machine is pinned.
rewind check
nix build --check says the output "may not be deterministic". rewind check runs the derivation twice with different seeds and jumps to the first step where the runs diverge.
a file
A failing build becomes a small file anyone can replay.
the clock
Wall clock time in the guest starts at SOURCE_DATE_EPOCH.

Limits, today

Userspace is never preempted. A thread spinning without syscalls stalls the guest. Futex-based code is fine.

Only interleavings that cross a syscall or a yield can be explored. Pure load and store data races between two threads are out of reach.

One vCPU per VM. Throughput comes from running many VMs at once.

x86_64 Linux hosts with KVM only, for now.
