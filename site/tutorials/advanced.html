Find who wrote a value

The worker crashed because p->queue was NULL. rewind blame finds the write that put a value there. Give it a step and an expression. It works out the expression's address in the thread that where picks. Then it replays the stretch of the run before the step, with that address in the CPU's debug registers. If the stretch holds no write, it tries the stretch before that: 

$ rewind blame 4736382d --at 4782 'p->queue'
rewind: process 166 at step 4782; loading symbols for 4 of its files
rewind: read 3 source files fetched from the VM earlier
rewind: walking thread 171's stack in gdb
rewind: process 166 at step 4768; loading symbols for 4 of its files
rewind: read 3 source files fetched from the VM earlier
p->queue = 0x0   8 bytes at 0x5556f833c068, thread 171, pool.c:77

last written at step 4768 by thread 166 (test_pool_shutd)
  pool.c:125  pool_shutdown  p->queue = NULL;
  was 0x5556f833c090

other threads just after the write, in step 4768:
  thread 171  pool.c:75  worker  futex_wait
  thread 172  pool.c:45  run_job  __syscall_cancel_arch

searched back to step 4117, 1 keyframe window, 1 write, 1.2s

The main thread set p->queue to NULL on line 125, in pool_shutdown. It did so at step 4768, 14 steps before the crash. blame also prints the value before the write.

The last part shows where the other threads were just after the write. Thread 171 is the worker that crashes later. It was on line 75, printing. It had already passed the check of p->stopping on line 74.

A step runs from one exit of the VM to the next, so a step can cover many lines of the program. At the start of step 4768, the main thread had not yet called pool_shutdown. rewind where --after-write looks just after the write itself, with the address and size blame printed:

--writes 2 goes back one more write. Here that is the calloc in pool_create.

blame can only watch values in memory. gdb keeps some values in registers, such as job here. For those, blame says it cannot watch them and lists the values on the same line that it can watch.

--reads lists the reads as well as the writes. It takes several expressions at once. It searches back to the start of the process, or to the step given with --since. Here it searches the last 40 steps. The output below keeps only lines 74 and 77 of the worker and lines 119 and 125 of pool_shutdown:

Read in order, the rows show the race:

1. Thread 171 reads p->stopping as 0 on line 74. So it goes on to count its job. 2. The main thread sets p->stopping to 1, then sets p->queue to NULL. 3. Thread 171 reads p->queue on line 77 and gets NULL.

The worker does not hold the lock between line 74 and line 77. Nothing stops the main thread from running in between.

In the app, the source panel underlines each value that blame can watch. Hover over a value to see where it is kept, or why blame cannot watch it. Click it to search. You can keep using the app while the search runs. The popover counts the steps searched so far, and the timeline marks the stretch being searched.

The answer names the write, the value before it, and where the other threads were. Click the write, or the button, to see the writer just after the write; click another thread to see it at that moment. The other buttons show the reads with one lane per thread, or blame the write before this one. The popover moves by its top line. At the step where the run failed, the panel starts searching for the failing line's values before you click.

Find the step that decides it

check names step 4758 as the one that decides it. Its passing run is the same schedule without that step, so the two runs are the same machine until 4758, where only the failing run gets a request to switch threads and a 640 µs pause of the running thread, and everything they do differently follows from it. rewind where names the thread that was on the CPU there: 

$ rewind where 4736382d 4758
rewind: process 166 at step 4758; loading symbols for 4 of its files
rewind: read 3 source files fetched from the VM earlier
rewind: walking thread 171's stack in gdb
process 166 (test_pool_shutdown), thread 171, at step 4758
#5 worker (src/pool.c:75)
      73  		long result = run_job(job);
      74  		if (!p->stopping) {
>     75  			printf("job %d done: %ld\n", job, result & 0xffff);
      76  			fflush(stdout);
      77  			p->queue->completed++;
arguments:
  arg = 0x5556f833c010
locals:
  q = <optimized out>
  job = 16
  result = 4092430570737637218
  p = 0x5556f833c010
called from #6 start_thread (pthread_create.c:454)
called from #7 __GI___clone3 (../sysdeps/unix/sysv/linux/x86_64/clone3.S:78)

A worker checks p->stopping without the lock, prints its job, and then counts it through p->queue, which pool_shutdown frees. At step 4758 the worker has made its check and is printing; a request to switch threads and a 640 µs pause of the running thread there holds it before the count. The test's main thread runs meanwhile, sees half the jobs done, and shuts the pool down, setting the queue to NULL, and the worker faults on it 24 steps later. Without that step's perturbation, the worker counts first and the test passes.

check --where looks up both threads itself: the one on the CPU at the deciding step, and the one at the failing run's first differing event. Each lookup forks the run and starts gdb, so it is opt-in: 

$ rewind check --where --epoch 1790985600 github:fzakaria/rewindvm#mylib 2>/dev/null | sed -n '/^where the threads were/,/first event that differs$/p'
where the threads were:
        4758   166/171   worker (src/pool.c:75), on the CPU at the deciding step
        4760   166/172   worker (src/pool.c:66), at the first event that differs

The first event that differs is the other worker, thread 172, at line 66, reporting the job it took off the queue. That is the cause showing up before the symptom: thread 171 is held at the deciding step, so the other worker and the main thread run ahead of it. Its fault at line 77, which rewind where showed at the top of this page, comes 22 steps later, at step 4782.

The fork stops before main nulls the queue in pool_shutdown. Going back, gdb shows the values swapped: the old value is the one after the write. reverse-stepi, reverse-next, reverse-finish and reverse-continue to a breakpoint work too. Rewind replays the run from the step's start to go back, so a step back takes a moment, and longer under exit time, which single-steps the way. A fork whose memory or registers gdb changed cannot go back.

Give programs more CPUs

The VM has one vCPU, so by default programs see one CPU and Nix builds run one job at a time. --cores tells them there are more, and the extra threads interleave on the one vCPU:

A command takes a run by its id or a prefix of it, by @ for the newest run and @2, @3 and on for the ones before it, by name, or by directory. rewind ls lists runs newest first, and filters them:

Rebuild a run exactly

A run's id is the hash of its inputs, which its manifest.json lists, so the same command follows the same run on a machine with the same CPU vendor and guest. rewind show prints that command with every input spelled out, including the epoch, which defaults to the start of the day the run was made. For a fork it prints its parents' commands first. @, the newest run, is the schedule 4 fork:

Script it

run, nix and fork exit with the job's status, as a shell would report it, so a shell loop can ask which schedules fail from a step: 

$ for s in 5 6 7 8; do rewind fork 4736382d 4682 --schedule $s --quiet 2>/dev/null; echo "schedule $s: exit $?"; done
schedule 5: exit 0
schedule 6: exit 0
schedule 7: exit 0
schedule 8: exit 0

check exits 1 when a run fails a property, by default by ending differently from schedule 0, and 0 when none does, diff 1 when the runs differ, cat 3 when the file did not exist at the step, and doctor 1 when this machine cannot record runs. With --json, commands print JSON for a program to read in place of their text: one object, or from ls and events one a line. check --json lists each run it tried under schedules, with the properties the run violated under violations. 

$ rewind ls --forks-of 4736382d --status failed --json | jq -r .id
0bd9caa5552224c9

$ rewind diff 3f364240 4736382d --json | jq -c '.divergence | {left_step, right_step}'
{"left_step":4759,"right_step":4760}

Judge runs by properties

By default check fails a run that ends differently from schedule 0. --property replaces that test with others, such as no-crash or single-writer=GLOB, and can be repeated. rewind check --help lists the built-in properties, and the properties tutorial explains each one.

A program that calls the Rewind SDK asserts from the inside: always must hold every time it runs, and sometimes must hold in at least one run. Check adds the sdk property when schedule 0 calls the SDK, and the app marks each failed assertion in red above the track.

A property can also be a script. It gets the run in $REWIND_RUN, can read it with rewind log, rewind events --json or rewind cat, and exits 0 when the run is correct or 1 with the reason on its first line. This one checks that bank's deposits add up: 

$ cat adds-up.sh
#!/bin/sh
# The deposits add up: bank prints its balance and what it expected.
line=$(rewind log "$REWIND_RUN" | grep "^balance ")
test "$line" = "balance 400, expected 400" && exit 0
echo "$line"
exit 1
$ rewind check --epoch 1790985600 --property script=./adds-up.sh github:fzakaria/rewindvm#bank | grep -E 'decides it|failing run violates adds-up'
rewind: packing 62 store paths for bank-0.1.0
schedule 1 violates adds-up, sdk; finding the step that decides it
step 3245 decides it: a request to switch threads there makes the run violate adds-up, sdk
failing run violates adds-up: balance 310, expected 400

--properties reads properties from a file, one a line, so a repository can keep them beside its tests. A script's path in the file is relative to the file's directory: 

$ cat rewind.properties
# What a correct bank run is.
no-crash
script=adds-up.sh

$ rewind check --epoch 1790985600 --properties rewind.properties github:fzakaria/rewindvm#bank | grep 'decides it'
schedule 1 violates adds-up, sdk; finding the step that decides it
step 3245 decides it: a request to switch threads there makes the run violate adds-up, sdk

Hold a task off the CPU for longer

A stall holds the running task off the CPU for at most 1.28 ms. A race whose window includes a sleep, a timer or slow I/O in another task needs a longer hold. This program gives eight threads 20 ms to start, built static: 

$ printf '#include <pthread.h>\n#include <stdio.h>\n#include <time.h>\n#include <unistd.h>\nvolatile int ready[8];\nvoid *work(void *i) { write(1, "started\\n", 8); ready[(long)i] = 1; return 0; }\nint main(void) {\n  pthread_t t[8];\n  for (long i = 0; i < 8; i++) pthread_create(&t[i], 0, work, (void *)i);\n  nanosleep(&(struct timespec){0, 20000000}, 0); /* 20 ms to start */\n  for (int i = 0; i < 8; i++) if (!ready[i]) { printf("worker %%d not ready\\n", i); return 1; }\n  puts("every worker ready");\n}\n' > ready.c
$ mkdir -p ready/bin
$ nix shell nixpkgs#pkgsStatic.stdenv.cc -c x86_64-unknown-linux-musl-cc -static -o ready/bin/ready ready.c

No schedule stalls a thread for 20 ms by default:

$ rewind check --root ready --schedules 64 --all --no-narrow -- /bin/ready
...
same result under all 65 schedules

--stall-max on run, nix, check and fork raises the longest stall, up to 1 s: 

$ rewind check --root ready --stall-max 50ms -- /bin/ready | grep -E 'ends differently|limited to|decides it|passing:|failing:'
schedule 37 ends differently from schedule 0; finding the step that decides it
schedule 37 limited to steps 318..340 still ends differently
step 339 decides it: a 40.96 ms pause of the running thread there makes the run fail
passing: run 25311d9f12c6f0e1, schedule 37 over steps 318..339, stalls up to 50 ms
failing: run d2da2643c66d7c2a, schedule 37 over steps 318..340, stalls up to 50 ms

The same steps stall, one exit in 128, but each stall picks one of the doublings of 10 µs up to the maximum, 14 of them for 50 ms, so fewer stalls are short. How often a race turns up then depends on how long it needs a thread held: 32 schedules of mylib crash 4 times by default and 5 times with --stall-max 100ms, in 6.7 s and 6.7 s. A stall is virtual time, so the guest's clock moves further, and a program's own timeouts see the extra time. The maximum is part of each run's spec, so rewind show, a replay and a fork of the run keep the maximum, and a run made without the flag keeps its id. A fork's own schedule takes the default unless it is given --stall-max too.

List directories in another order

Inside the VM a directory lists its entries in the same order in every run, so a build that depends on that order never differs there. On a real machine, ext4 lists a directory in an order set when the disk was formatted. The kernel argument rewind.dirents=N lists every directory the build sees in the order of a hash of each name keyed by N, as another ext4 disk would; 0 keeps the usual order. The key is part of the run, so a run made with one replays: 

$ rewind nix --kernel-args rewind.dirents=2 github:fzakaria/rewindvm#mylib

rewind check --dirents 3 builds under keys 1 to 3 besides the stock order, a line each, and reports the first key whose build ends differently; rewind diff --outputs shows what it changed. setuptools 80.9.0 builds a wheel that names its own version as 1.0 under key 2, because it reads its version from whichever .egg-info directory lists first. Directory order in the design notes says how the kernel does it.

Move around a long run

Builds of larger projects run to hundreds of thousands of steps. The app has keys to jump to a step, step between events of one kind, bookmark, search and zoom the timeline. The ? key lists them all:

Hand a failure to someone else 

$ rewind export 4736382d --replayable -o crash.rwd
rewind: wrote crash.rwd (201.5 MB)

$ REWIND_HOME=elsewhere rewind import crash.rwd
4736382dc2ed9626  exited:2          4821 steps  mylib-0.3.0

$ REWIND_HOME=elsewhere rewind replay 4736382d
identical to the recording: 1687 events and 1476 read and write records over 4821 steps, and the whole machine at its 9 keyframes

A replayable export carries the keyframes, the image and the VM's kernel, and replays on any machine with the same CPU vendor. Without --replayable it is the events alone, 22.9 KB: enough to read and to scrub in the app, whose Export button writes the replayable kind. Both kinds carry the run's bookmarks.

The other machine also needs the features of the run's CPU model. A run without --cpu gets v3, whose features include ERMS, the fast rep movsb flag. On a host that lacks only ERMS it gets v3-compat instead, the same CPU with ERMS hidden, and rewind prints a line saying so. A v3 run needs a host with ERMS, and a v3-compat run replays on hosts with or without it. A replay on a host without the model's features names what is missing and where the run replays, and rewind doctor says which model a run gets on a machine.

With counter time the VM's clock follows the work done inside it; with exit time computation takes no virtual time. --clock picks one. Counter time explains. rewind doctor checks the clock with KVM, gdb and the rest of what rewind uses, and says what to do about each problem.

Find where a run hung

A thread gives up the VM's one CPU only at a step, so a loop that makes no system call keeps it, and the run hangs. --timeout stops a run after that many seconds on your machine. When the guest had gone a second or more without an exit, rewind says where it was stuck. A program that spins, built static with its symbols: 

$ printf 'volatile unsigned long n;\nint main(void) { for (;;) n++; }\n' > spin.c
$ mkdir -p spin/bin
$ nix shell nixpkgs#pkgsStatic.stdenv.cc -c x86_64-unknown-linux-musl-cc -static -g -o spin/bin/spin spin.c
$ rewind run --root spin --timeout 5 --name spin -- /bin/spin
rewind: run 4175e7e086c0c6f4 timed-out after 301 steps, 0.002s virtual, 5.010s wall (timed out computing without exits for 4.3s, in user space in main+15 (spin.c:2), process 34 (spin))

A run that timed out while still making exits was slow rather than stuck, and says so. rewind check gives each perturbed schedule ten times as long as schedule 0 took, at least a minute, and reports a stuck schedule the same way. Schedule 0 itself has no limit, since a long build is no reason to stop it, so a test suite that hangs there holds up the whole check. Give such a suite rewind check --timeout, which bounds every schedule, schedule 0 included. --status timed-out lists the runs that timed out: 

$ rewind ls --status timed-out
4175e7e086c0c6f4  timed-out          301 steps  spin

Keep the run directory tidy

Runs live under ~/.local/share/rewind, or REWIND_HOME:

$ REWIND_HOME=elsewhere rewind ls
4fe1061ad78df32f  exited:0          6502 steps  mylib-0.3.0 (fork of 4736382dc2ed9626 at 4682, schedule 2)
0bd9caa5552224c9  exited:2          4833 steps  mylib-0.3.0 (fork of 4736382dc2ed9626 at 4682, schedule 1)
4736382dc2ed9626  exited:2          4821 steps  mylib-0.3.0

$ REWIND_HOME=elsewhere rewind remove 4fe1061a
removed 4fe1061ad78df32f
rewind: `rewind gc` removes the pages no run uses any more

remove takes a run with every run forked from it. To remove every fork and keep the runs they came from, run rewind ls | awk '/fork of/ {print $1}' | xargs rewind remove. prune --identical removes forks that ran exactly as an older one did.
