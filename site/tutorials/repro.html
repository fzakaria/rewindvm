Tutorial: reproducible builds

A build is reproducible when the same inputs give the same bytes, so anyone can rebuild a package and check that it matches the one they were given. Rewind VM fixes every input of a build, down to its random numbers, the order its threads run in and the order its directories list in, so one build follows the same run every time. Change one of those inputs and build again: if the output changes, that input changed it, and both runs are kept to replay and compare.

The examples are tiles and plugins from examples, two small builds that each write one text file. Install Rewind as the Nix tutorial does.

Build it under eight seeds

tiles writes its pkg-config file with a Python script that keeps the packages it links against in a set. Python iterates a set in an order drawn from its hash seed. nixpkgs pins that seed with PYTHONHASHSEED=0, and tiles unsets it.

A run's seed decides every random number the build draws, including Python's hash seed. check builds tiles under eight seeds, each with the default schedule only:

Who wrote it

rewind blame takes two runs and a file, and names the program that wrote the first byte that differs: 

$ rewind blame a88c945d 206bd357 /nix/store/ihhhzc5qphjjz5vgss7swki10dwkicsb-tiles-0.2.0/lib/pkgconfig/tiles.pc
tiles.pc differs at byte 178. python3 (pid 112) wrote that byte at step 2,901 in run a88c945d and at step 2,901 in run 206bd357.

22 of 227 bytes differ. The bytes from byte 178:
  a88c945d  70 69 78 6d 61 6e 2d 31 2c 20 6c 69 62 70 6e 67  |pixman-1, libpng|
  206bd357  7a 6c 69 62 2c 20 70 69 78 6d 61 6e 2d 31 2c 20  |zlib, pixman-1, |

Who wrote the file in run a88c945d, from the last writer back:
  install (pid 122) copied it from /build/tiles/tiles.pc, starting at step 3,149. Its source already differs, so the copy did not cause the difference.
  bash (pid 112) wrote /build/tiles/tiles.pc, starting at step 2,788. It is the first writer, and the file already differs when it is done.
Run 206bd357 made the file the same way, with the same programs.

In both runs, one write of 227 bytes, from byte 0, set byte 178.

python3 ran with the same command line in both runs, so the difference comes from something it read or from randomness.

What python3 read:
  1 file that the build made, all the same in both runs: /build/tiles/gen-pc.py.
  31 other files that the build did not make, such as programs and libraries.

Likely cause: something inside python3 (pid 112), such as randomness or the order its threads ran in. Its command line and the files the build made that it read are the same in both runs.

The first line is the answer: python3, pid 112, wrote that byte at step 2,901. The lines after it show how blame got there. install only copied a file that already differed. Before that, pid 112 opened /build/tiles/tiles.pc while it was still bash, for the > redirect, then became python3. python3 had the same command line and read the same gen-pc.py in both runs, so the cause is inside it, and the seed is the one input that changed.

Blame works from records the guest kernel keeps in every run: each write to a file, and each file a program opens. It finds the write that set the byte without replaying either run.

Directory order

plugins writes an index of the plugins it ships, in the order os.listdir returns them. Under eight seeds it reproduces: 

$ rewind check --epoch 1790985600 --seeds 8 --schedules 0 --all --no-narrow .#plugins
...
0 of 7 other runs ended differently
same result under all 8 runs

A directory lists in the order its filesystem keeps it. In the VM that order is the same in every run: /build lists its newest file first. On a real machine, ext4 lists a directory by a hash of each name, keyed by a seed chosen when the disk was formatted, so two machines can list one directory in two orders. The guest kernel does the same when its command line has rewind.dirents=N: every directory lists in an order keyed by N. check --dirents 3 builds it again under keys 1 to 3 and compares each build with the stock order, dirents 0: 

$ rewind check --epoch 1790985600 --seeds 1 --schedules 0 --all --no-narrow --dirents 3 .#plugins
dirents  0 schedule   0: exited:0             3887 steps  77b96f07540a  run 130eba8588e5a0b0
dirents  1 schedule   0: exited:0             3887 steps  3d555b541296  run dddd0c1fedf9b1e1
dirents  2 schedule   0: exited:0             3887 steps  925dde4ef23a  run 371fc50a1604a75e
dirents  3 schedule   0: exited:0             3887 steps  abd7877043a8  run 875809d42feba5fc
3 of 3 other runs ended differently

The key is one of the run's inputs, so each order replays.
