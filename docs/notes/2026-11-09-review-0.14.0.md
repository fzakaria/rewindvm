# Review of Rewind 0.14.0

Written 2026-11-09 against revision `a552c79d`. Gone through item by
item on 2026-11-10; each item was taken, deferred or dropped. This
document now has three parts: the decisions and what came of them, what
is fixed on main with the commit for each, and what is deferred, kept
here in full so nothing has to be rediscovered.

[preemption.md](../preemption.md) (the landed design and the prototype's
measurements, commit `a00e40db`), and the multicore options to
[multicore.md](../multicore.md) in the `multicore-investigation` workspace

## Fixed on main

The four fix stacks were rebased onto main on 2026-11-10 with no
conflicts and the full test suite passed on the result. The ids below
are the ids on main.

### CLI and trace

- `rewind diff --file` said two files were the same when they differed
  past the first megabyte (`3953a84a`).
- `rewind diff --outputs` missed files that were moved by renaming
  their directory, which every multi-output Nix build does. It now
  also lists files it could not compare (`308c32bd`, `78a80c5d`).
- `rewind blame` printed "pid 1234" in place of the program's name for
  a write made just before the program exited (`ec62e45c`).
- `rewind blame` named the wrong program when a pid had been reused
  (`f8026e3e`).
- A test report cut short by a killed test runner aborted the whole
  `check`. It is now reported as that schedule's failure (`cc5308a6`).
- The `no-orphans` property reported every process of a hung run as
  left behind (`198d9882`).
- A failed export destroyed the file it was replacing (`271bef48`).
- Importing a recording of a run you already had overwrote its
  manifest and inputs. Import now also refuses a recording whose
  inputs do not match its id (`bb89efa6`).
- `rewind show` printed a command that made a different run for some
  forks. It now prints the seed, or says no single command makes that
  fork (`eb7435a1`).
- `rewind gc` now removes what killed image builds and imports left
  behind (`d2b01199`).
- Looks at a run stop when their answer is complete; `rewind cat` in
  the middle of a run went from about 0.56 s to about 0.30 s
  (`ca8ce9bd`).

Three of these change what users see. `rewind show` now fails for
forks that `check --run` narrowed. `rewind import` can refuse a file.
The repro tutorial's "2 of the 5 files" may show another count when it
is next recorded.

### Engine

- A timed-out run did not replay, so `check` refused hangs it found
  (`4455279e`). See decision 3.
- Runs that ended idle or timed out lost up to 4,096 steps of context
  switches at the end, the ones that explain a deadlock (`e8bc1e56`).
- A replay that skipped a recorded event, or stopped short of the step
  asked for, was accepted. This was finding A4 of the October audit
  (`f1243f04`).
- gdb never stopped at a breakpoint once the program's first thread
  had exited (`282bbb7a`).
- `reverse-continue` kept returning to the first of several hits of a
  breakpoint (`848b3720`).
- `replay --bisect` reported a bug in Rewind when the difference did
  not occur on its last try (`a3d1b3d9`).
- `reverse-continue` closed the gdb session when a watchpoint needed
  three debug registers (`64bc9253`).
- A watchpoint on a very large array used gigabytes of memory
  (`3f893f7c`).
- Stopping at a branch count failed on hybrid Intel CPUs when the
  thread moved between kinds of core (`79c95d4f`).
- A recording made on Zen 4 could not be looked into on Zen 3, because
  restoring a keyframe set CPU registers the older CPU lacks. Verified
  on leviathan (`25807f60`).
- `rewind shell --with` silently left the fourth package off PATH. It
  now refuses (`e0e9c648`).
- Under `--cpu host` the monitor could not read user memory at all. A
  single step across a system call ran the whole call, and gdb could
  not read memory. No check ran gdb under `--cpu host`; one does now
  (`31d05846`).
- Two smaller ones: `d8554510`, `b6ed11e3`.

- An import finishing closed whatever the user had opened meanwhile

Checked by unit tests only:

- Search ran on the UI thread and could show another run's results
  (`ca0846ee`, `2deed81a`).
- Process names ignored the playhead, so a reused pid showed the wrong

  `d3bdcd4f`).

  read, was reported as no license (`009f7554`).
- Others: `9cad2b59`, `fa86d03e`, `c950f79f`, `cd4bd28e`, `9acc6b59`.

Four choices inside these to know about: any output in the shell pane
now clears a selection; the Threads tab no longer pans left of step 0;
a click that closes a context menu no longer also acts on the row under

The viewer page now numbers a file read when it starts, so of two
files, or a file and a fetch, the one asked for last wins however their
bytes arrive, and a read the browser fails is reported in the app's
notice (`e0eff5f1`). Checked in a headless browser with a damaged zip,
a file that is not an export, and a slow read overtaken by a fast one.

### Wording and exit status

- Every command exits 2 when it could not do its job; 1 stays "found a
  difference" for `diff`, `replay`, `blame`, `check`, `doctor` and `pmu
status`; `cat` and `files` keep 3 and 4. The convention is in `rewind
--help` and in the advanced tutorial (`55213c70`). No release notes
  are kept in the repository; the release workflow generates them from
  commits.
- One voice: keyframe for snapshot, initrd for initramfs, step for
  exit, VM for guest where the whole machine is meant (`10f722a7`).
- Six messages say what is true: the home message names the release's
  `bin/rewind` launcher; the exit-time warning says what `pmu enable`
  gives; `doctor`'s plural and its line without the program name;
  twelve internal states go through one `internal error ... rewind
bugreport` helper; "not supported yet" is "not supported";
  `--schedule`'s help no longer says "seed" (`0f71cdad`).
- `docs/pmu.md` and the counter time page say `sleep 10` takes ten
  seconds on the VM's clock; the README's first command is `rewind
check github:fzakaria/rewindvm#mylib`; the first tutorial defines
  step and keyframe at first use; the advanced tutorial's exit statuses
  are a table (`fdf06366`). Templates only; the tutorials show the
  changes when next recorded.

### Page store and home

- The store drops index entries whose pages are not in its files when
  it opens with no other process using it, so a power loss or a full
  disk no longer leaves pages the store believes it has (`091def67`,
  decision 10).
- The first keyframe lists only pages that were written, so its cost
  no longer grows with `--mem` and no longer faults in every untouched
  page. At 1 GiB the walk was inside the measurement noise, so no
  number is claimed (`36a4bbb0`).
- A run is found by name or age from an index of runs in the home
  (`cache/runs.json`), rebuilt when it disagrees with a manifest.
  `rewind show <name>` on a home of 6,000 runs went from 379 ms to
  33 ms (`02a3b7ae`).

### Engine, second round

- `rewind build` refuses an output entry under a symlink or a file, so
  a build that takes over its VM cannot write outside its outputs
  (`93efff55`).
- `remove`, `prune` and the paths that register a run hold the runs
  while they work, so a prune during `check --run` cannot delete a
  fork's parent (`0511236a`).
- A file stays open while a forked child holds its descriptor, so a
  viewer no longer shows an early version at a later step (`ec401ffb`).
- `rewind gdb` reads symbols, and the kernel debug directory a
  manifest names, only from written-out store paths (`7108b739`).
- One store that hits several watches reports each of them; the
  gdb-watch check covers a 64-bit store over two watched halves
  (`5d90b14b`).
- gdb's Ctrl-C stops a guest that makes no exits, in about 30 ms, and
  SIGTERM (the app's Cancel) ends a replay or inspection in 17 to
  29 ms with "interrupted"; nothing about the interruption reaches the
  trace (`063f8b46`).
- A single step across a page fault with all four debug registers in
  gdb's hands borrows one and lands where a replay does; new check
  gdb-fault (`2a546200`).
- `blame` and `reverse-continue` search several keyframe windows at
  once and still return the nearest hit. On a write 301,000 steps
  back, blame went from 8.4 s to 4.4 s and a reverse-continue session
  from about 20 s to about 12 s on the laptop (`58a71147`).

gdb-step failed once on leviathan with a recording of `/bin/fork` that
exited 127 under an unusual run id, and passed on two later builds.
The cause was not found.

### Check and VM memory

- Keyframes are flushed to disk eight at a time instead of three
  flushes each (`e192ed4d`).
- A check's runs share one page store, which saves each run the
  163 ms or more and 49 MiB of reading the index's unsorted tail
  (`cecb06c4`).
- A run that takes no keyframes maps RAM in 2 MiB pages, without
  KVM's dirty log; a machine without the log refuses to take a
  keyframe rather than list no pages (`f8df2fed`).

- `rewind check` starts its first batch of schedules beside schedule
  0, once schedule 0 has flushed the keyframe they fork from and passed
  the step that covers them, and each later seed's batch beside that
  seed's unperturbed run. Output and verdicts are unchanged; new check
  check-overlap holds that (`6130d0ac`, decision 12).
- The dirty-log test builds its machine on the host's own CPU model,
  so the `rewind` package builds on a host without ERMS (`761cf24a`).

Measured on leviathan, five rounds each:

| Change                      | Workload     | Before   | After     |
| --------------------------- | ------------ | -------- | --------- |
| Overlapping check           | hello check  | 51.2 s   | 28.9 s    |
| Overlapping check           | its peak RSS | 1260 MiB | 1530 MiB  |
| One page store, 2 MiB pages | check, hello | baseline | within 1% |

The shared store helps only a home whose index has a large unsorted
tail, which a fresh benchmark home does not. Leviathan's transparent
huge pages use deferred defragmentation, so guest RAM faults in as
4 KiB pages there whatever the dirty log does; the laptop was not
measured, so no gain is claimed for 2 MiB pages yet.

A later seed's batch can start and then be dropped when that seed's
unperturbed run already ends differently. The check now notes each run
directory it made itself, and removes those runs when it drops the
batch, through the same path as `rewind remove`; a run with the same id
that existed before is kept (`c6d4df6b`). One gap remains: if another
process executes a run with the same id after the batch made its
directory and finishes before the drop, that run is removed too. With
`--dirents`, the first seed's batch does not start early.

### Manifest and processes

- The engine writes the run's verdict into the manifest when the run
  ends, with every reason it failed; `rewind ls`, `check`, `show`, the
  app and the viewer read that field and judge nothing themselves
  (`37d6ae43`, decision 6). Runs that exit 0 but break an assertion now
  say so, which changes output the properties, points and advanced
  tutorials show.
- A process's name at a step and the unpacking of an export each have
  one function, used by both the engine and the app; the app now
  refuses a symlink in an export, as the engine did (`b84f6e7c`).
- Each life of a pid has its own id, the step it was forked at, so
  blame, the process tree, the failure chain, properties and the
  Threads lanes stop confusing a reused pid; the per-site workarounds
  for reused pids are gone (`52d057b7`). The trace format did not
  change.

### Desktop app, second round

- The flaky run test was a lock held by a forked child's copy of the
  descriptor; the test now releases it explicitly (`75263050`).
- The app calls the CLI "the rewind command" everywhere and says
  Delete (`e294daa4`).
- A pasted license, or one given with `--license`, whose updates end
  before the installed one's no longer replaces it (`1b2eab5c`,
  `b6387e17`).
- The engine commands the app starts are stopped when it quits
  (`e5271d97`). Its test failed once in five full-suite runs on the
  combined line, when a parallel test held the stand-in script busy;
  it now retries like its neighbours (`fb856473`), and 90 runs since
  passed. One failure in the 15 runs before those was not captured.
- Per-frame work measured on a home of 6,233 runs and an 82,000-event
  run: the Files list went from 221 ms to 0.11 ms a frame, the Threads
  card from 37 ms to 0.03 ms, and the start screen from 27 ms to 12 ms
  (debug build) (`1489dbc4`).
- What belongs to the run on screen is one struct, replaced whole when
  the run changes (`326b93c9`).
- The two-run hex dump finds the byte under the pointer through the
  registry, the pattern the release build is known to survive. It
  worked in a release build under Xvfb; the old code's crash was not
  reproduced first (`e873cd96`).

### Viewer, second round

- The viewer reads an export only as far as the run: for the devenv
  case study's 187 MB replayable export it read 4 MiB and opened the
  run. The shared tar walk can now stop at a member, and the desktop
  app stops at the same place instead of decompressing a whole
  replayable export to learn it was one. A walk that reaches the end
  must find the archive's closing block, which fixes `rewind import`
  accepting an export cut short at a member's edge (`45366d1f`).
- A fetch the browser refuses names the hosts that work: raw file
  links and GitHub Pages, not release downloads (`cb955e4a`). The
  schema-migration case study already serves its trace from the site;
  its 543 MB replayable export is over GitHub Pages' 100 MB limit and
  stays a plain download.
- The link carries the tab, the selected thread and the search text,
  and a Copy link button copies it; step-only links still open
  (`90661ad7`).
- Where a pane says a feature is in the desktop app, it shows the
  `rewind-app` command that opens this recording at this step, with a
  Copy command button (`cb065e31`).

### Guest, second round

- The guest skips the boot-time rewrite of every trace event's print
  format, which took 100 to 390 ms of every boot. Turning off the
  kernel's tracing core instead does not link, since Linux 7.2 emits
  event-tracer code for every tracepoint, so a small guest patch stops
  `trace_eval_init` from queueing the rewrite. An `echo` run went from a
  median of 306 ms to 204 ms on the laptop, and its guest time from
  198 ms to 81 ms (`9cea173d`).
- A process's exit is recorded when its last thread exits. A main
  thread that calls `pthread_exit` is a thread exit, and the process
  lives on with its workers; `rewind summary` now names the failing
  step of such a run (`1d029888`). The host stopgap from the answers
  work was folded back into this.
- Found along the way: `rewind run --root` failed on a root given as a
  symlink to a directory (`02c8770f`); the file-events, signal-once and
  switches checks had each been failing for reasons in the checks
  themselves (`64091469`, `28e3bb70`, `d0208dbf`); the design doc
  named two guest patches where there are seven (`71b37e13`).

- A run whose guest went idle for good never stopped: virtual time ran
  on without end at about 92% of a host CPU. This was older than
  interface 6 (0.13.0 hangs the same way). The guest always had a timer
  armed: kcompactd's proactive compaction every 500 ms, `crng_reseed`
  and conntrack's `gc_worker` every 60 s, dirtytime writeback every
  12 h, and the tick's own cap on an idle sleep. The guest config turns
  proactive compaction off, the clocksource no longer caps an idle
  sleep, and the three periodic jobs are deferrable, so they still run
  on time while the CPU is busy. The inspect-idle run now stops as
  stalled after 1,655 steps in 0.35 to 0.56 s; a guest waiting on its
  own timers still wakes for them, and replays identically. Looking at
  the last steps of a run that ended idle failed once the run could
  end that way, and is fixed in the same commit; the check now fails
  after 120 s if a run does not stop (`414e7b63`).

The guest changes ride on 0.15.0's interface 6, with no second bump.

### Exports with answers, second round

- Sources gdb fetched through debuginfod are named as their DWARF
  names them. Before, 25 of 31 source paths in a mylib export's
  `answers.json` were the exporter's debuginfod cache paths under their
  home directory, and `rewind where --json` printed the same
  (`ca5c9024`).
- A file read that fails is recorded with its error, where it was
  recorded as a file the VM sent no bytes of (`d8480dd8`).
- A process whose main thread called `pthread_exit` while other threads
  ran had no threads answered after that point (`9ff73dfd`). The cause
  was in the guest, fixed in `1d029888` below.
- Each process at an answered step is walked by one gdb session, with
  the steps and processes on a pool of workers sharing one debuginfod.
  The answers are byte-identical to the serial code's at 1 and 8
  workers (`426ca2a7`).

| Run, warm caches             | Before | After  |
| ---------------------------- | ------ | ------ |
| 17 threads, failing at exit  | 5.8 s  | 0.4 s  |
| GNU hello build, 8 bookmarks | 40.7 s | 12.3 s |
| mylib's failing run          | 4.3 s  | 1.6 s  |

Measured cold, gdb was 70 to 80% of an export's time and seeking under
10%, so one forward replay was ruled out.

### Guest interface 6 (decision 5)

- RDTSC traps in every guest task, including those kernel threads
  start and everything under `rewind shell`, and `prctl` cannot lift
  the trap (`9b6f9058`).
- File events name the path the kernel resolved, so a symlink on the
  path no longer gives one file two names; opens relative to an
  `O_PATH` descriptor and `openat2` are reported. A failed open, unlink
  or rename was already no event, since events are written on a
  successful return; checks.file-events now asserts it (`64b40e64`).
- A crash on a worker thread is reported once (`d4c2f6bd`).
- Looking at the last steps of a run that ended idle works: the idle
  verdict moves from the idle exit to the next guest entry, and the
  guest checks for work before it reports idle (`09340ed8`).
- A process whose leader exited is read through a live thread's map,
  and gdb's fallback to an earlier step is gone (`7651485c`).
- The monitor loads the uncompressed vmlinux and the guest kernel no
  longer walks its pages for W+X at boot. `echo` went from a median of
  382 ms to 290 ms on the laptop under `--clock exits`; the first entry
  into the guest, which was decompression, went from about 300 ms to
  about 23 ms. The release ships `share/rewind/vmlinux` in place of the
  bzImage. The unexplained 64 ms during boot was not found
  (`b29a6bdf`).
- The guest interface is 6 and the monitor accepts only 6, with the
  support for interfaces 3 and 4 removed (`631bc9fb`). Every recording,
  keyframe, tutorial, example run and case-study export has to be made
  again.

### Run summary and packed answers

- `rewind summary <run> [--compare <run>]` prints the verdict and its
  reasons, how the run ended, the failing step with its process and
  thread, the last 20 lines of output, and where two runs part. It
  exits 0 for a passed run, 1 for a failed one, 2 on error. Every export
  carries the same text as `summary.txt`, and the viewer shows it below
  960 px wide, computing it in wasm for an export without the file. A
  phone that opens a link with `url=` now downloads the wasm to do
  that. `rewind export` now refuses a run whose trace does not decode
  (`a67c2a55`, `d24f46d8`).
- `rewind export --with-answers` stores, at the failing step, each
  failed assertion and each bookmark, where every live thread is in the
  source and the files the job had written, up to 1 MiB a file and
  32 MiB in all, with what was left out listed. The viewer answers
  source and file questions at those steps and keeps the desktop-app
  notice elsewhere. Each answered step costs one fork per live thread
  and one for files, not one forward replay; the desktop app does not
  use the answers (`c9913cf5`, `4e0a69e3`).

### Design observations now covered

- Every way a run can end finished the trace differently; the two most
  serious engine bugs came from this. The engine has one routine for
  all of them (`e8bc1e56`).
- The app reset per-run state by listing fields in three places; one
  struct replaces them (`326b93c9`).
- The same fact was computed in two places: whether a run failed, a
  process's name at a step, and unpacking a recording. Each now has one
  function (`37d6ae43`, `b84f6e7c`).
- Readers identified processes by pid while the guest reuses pids. Each
  life of a pid now has an id (`52d057b7`).
- The app started engine commands it could not stop. They are stopped
  on quit (`e5271d97`).

File events were thought to record attempts. They are written on a
successful return, so a failed call was never an event; a check now
holds that (`64b40e64`).

### The first screen of the landing page (decision 9)

A visitor with a flaky test learns from the first screen that Rewind
runs things deterministically and has a timeline. They do not learn
that `rewind check` finds the failing interleaving for them. That
claim first appears four sections down, and the headline, "Scrub any
run back to the step that broke it", assumes they already have a
failing run. The word "step" is in the headline and is defined 180
lines later. "Schedule" is used four times and never defined.

The headline and lede are the owner's copy. The suggestion is one more
sentence in the lede: "`rewind check` reruns it under other thread
schedules until one fails, and names the step that decides it."

The Limits list also leaves out the Go garbage collector hang, which a
Go developer meets on their first run.

### One boot keyframe for all runs with the same kernel

Investigated on 2026-11-10 and not built. In the owner's home every
run's first keyframe is at step 256, not at boot, and lists about
16,200 pages (63 MB, a 583 KB keyframe file). Between runs of the same
kernel 93% to 99.9% of the page hashes are identical; the pages that
differ are the boot parameters, the command line (`--cores`), kernel
data pages that follow `--epoch`, `--cores` and `--seed`, and the job
archive at the top of RAM. The page store already deduplicates by
hash, so the shared pages are stored once. What a shared base keyframe
would save is the 583 KB file per run (about 340 MB over the 590
keyframed runs in that home) and 16,200 index lookups; it would not
save the hashing, since finding the pages that differ from the base
needs every page's hash. In exchange a keyframe that runs across runs
depend on would need an ownership rule in `gc` and `remove`. Not worth
it at this size.

A second look the same day measured an `echo` run on 0.15.0 phase by
phase. A shared base keyframe file would save about 440 KB and 6.5 ms
per run, about 0.75% of the owner's 46 GB home. A shared snapshot that
runs restore instead of booting would save about 350 ms of a 613 ms
run today. It needs the guest reordered so that the seed, epoch,
cores, job and image all enter at one point after boot, which changes
what `--seed` and `--epoch` mean before that point. The boot itself
has a cheaper fix: at step 152 a kernel work item,
`eval_map_work_func` from `trace_eval_init`, rewrites the print
formats of every trace event, and it took 195 to 324 ms in every
sample, about 60% of the guest's time for the whole run. Nothing in
Rewind reads tracefs. The guest patch uses raw tracepoints, so the fix
is to keep those and stop that update. The recommendation: make that
guest fix, drop the shared base file, and measure the shared snapshot
again afterwards. The scripts are in the review session's scratchpad
under `kf/`.

### Parallel replay

A replay runs the whole recording in order on one core. Keyframes make
it possible to split: give each of several workers a stretch of the
run, have each start from the keyframe at the head of its stretch and
check through to the next. For the hello build on leviathan that
should take replay from 22 s to about 5 s with 8 workers; that is an
estimate, and nobody has built it.

Why it was deferred: the check is weaker, since state the keyframe
comparison leaves out (the TSC MSR, three Hyper-V MSRs, the APIC timer
count, the performance counter MSRs) is restored rather than
recomputed, so a divergence that lives only there passes in pieces and
fails in order. Each worker pays a keyframe restore, which is store
page reads, and eight VMs alive at once is eight times the guest
memory. Runs recorded with `--no-keyframes`, which is all of check's
narrowing runs, cannot be split. The bracket a differing keyframe
reports, the "replays the stretch where it changed" warnings and
`--bisect` all assume one replay in order. If built, offer it as
`replay --jobs` and keep the in-order default.

### Using Rewind to find performance problems

The field test (artifact NW542PJb) ran nine programs 16 times each,
once untouched and 15 times with the random pauses `rewind check`
uses. It looked for stretches where the CPU was idle while the program
still had threads alive, and asked `rewind where` what each thread was
doing in each one. It found two real problems: the `ignore` crate,
used by fd and ripgrep, sleeps a millisecond at a time while it waits
for work, and jj holds one lock across writing every new file. Both
fixes measured faster natively.

It was hard to act on for three reasons. It answers a different
question: the output lists where threads waited, where someone tuning
a program wants to know which wait, if shorter, would make the program
finish sooner. Its headline number cannot see the most common
contention: the VM has one CPU and does not interrupt a computing
thread, so a lock taken, held while computing and released is never
contended; only locks held across a system call show up, and more
schedules do not fix that. And it is expensive: one replay per live
thread per idle stretch, 29 minutes for ripgrep and 47 for jj.

What Rewind can say exactly: the VM has no network and no outside
input, so when its CPU is idle the only thing that can end the idle is
a timer some thread set, and every idle nanosecond can be charged to
one cause. A run's time on the VM's clock is then fully accounted for:
computing, split by process and thread, plus idle, split by the wait
that ended each stretch, the same on every run.

The proposal, deferred until there is a reason to build it:

1. A command, here called `rewind time`, that prints where the time
   went. A sleep that runs to its timeout is listed apart from a wait
   another thread ends, because the first kind is where polling loops
   and retry delays show up. Best use expected on builds and test
   suites: "a fifth of this test suite is `sleep 1`".

       $ rewind time RUN
       30.6 ms on the VM's clock
         18.5 ms computing
             18.1 ms  fd, 9 threads
              0.4 ms  everything else
         12.1 ms idle
             12.0 ms  40 sleeps that ran to their timeout, 0.3 ms each
                      fd: get_work, ignore/src/walk.rs:1980
              0.1 ms  2 waits ended by another thread

2. Work and span of a threaded run: work is all computing added up
   (time on one CPU), span the longest dependent chain (time with
   unlimited CPUs). Work divided by span is the number of CPUs the run
   can use; the chain names what to shorten. The field test measured
   jj's snapshot using about 1.6 of 16 cores natively; this number
   would have said the same from one recording.
3. A gate for CI: `rewind time --max-idle 5%`, a number that does not
   move with the build machine's load.

What it takes: the guest adds to the context switch record the address
the thread was at in user code, and a new record of which thread woke
which. Both were left out of the 2026-11-10 guest batch on purpose,
since a record nobody reads is untested code; add them when the
command is built.

What it would still miss: contention on a lock held only while
computing, spinning, and lock-free retries, which make no system call.
Native tools such as `perf lock contention` see both. The field test
never compared its jj finding against those tools, and that comparison
is the test of whether this is better than what exists.

### The viewer

- **Old links will break when the trace format changes.** The viewer
  is always the newest build. When the trace format moves, every link
  shared before then shows an error with nothing the visitor can do.
  Keep the last viewer for each format at its own address. This
  matters before 0.15.0 ships, since that release changes the trace.
- **Recordings carry paths from your machine and the job's
  environment.** One published example contains
  `/home/fmzakari/.cache/...` in its manifest. An export meant for
  sharing should replace such paths and let the user leave out
  environment variables.
- **The start screen's examples** leave out the schema-migration and
  devenv case studies.
- **A phone or a screen reader gets nothing.** Below 960 pixels the
  page shows a note and a link to a video. The plain-text summary (in
  progress) is what a phone should show.
- **A GitHub action** that runs `rewind check`, exports the failing and
  passing runs, and comments on the pull request with the summary and
  a viewer link. Needs the summary and a host the viewer can fetch
  from.
